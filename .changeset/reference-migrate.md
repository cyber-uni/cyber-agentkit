Add `reference migrate [name...]`, which finds the reference files still in a form version 1 wrote, and the files under a name a plugin renamed, and prints the plan: each file, its tier, the form, what it is now, and what it becomes. It writes nothing unless given `--write`, which applies every change and returns the same plan. It reads the `repo` tier, the `user` tier (whose files no git history restores), and every project section below the root; with `--plugin <folder>` or `--default <folder>`, only that source folder in the repository. It never changes a managed file or an installed plugin or skill. `merge: merge-sections` is removed, `merge: first-wins` becomes `merge: replace`, `overrides` becomes `extends`, a skill's `references/<name>.md` becomes `<name>.default.md` for a name given with `--default`, and a file under an older name, from a plugin's `references/_renames.yaml` or an owner's `aliases`, is renamed to the new name with its metadata file. A change it cannot make safely, such as a selection in a project folder or a rename onto a name that already has a file, is a manual row saying why. The library exports `migrateReferences`.
