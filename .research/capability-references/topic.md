# Capability references (November 2026)

## Question

Should the reference system formalize a **capability reference**, a reference that describes what one system can do so
a skill can be generated or customized for it? If so, what goes into one, what counts as a system, how does one stay
current, and how does it relate to interfaces? (cyber-agentkit#366.)

## Scope

In scope: repobuddy's tracker references and the skills that read them; this repository's reference spec and interfaces;
capability descriptions in other ecosystems and how they stay current. Out of scope: building anything, and changes to
repobuddy (read only).

## Source angles

- Practice in our own tools: repobuddy's `project-tracker.capabilities` interface, its implementations, and its skills.
- This repository's reference system: interfaces, cardinality, `check`, `implementations`, `create --implements`.
- The owner's second brain.
- Other ecosystems: LSP and MCP (negotiated capabilities), OpenAPI and Arazzo (static descriptions and workflows over
  them), MDN browser-compat-data and Terraform schemas (matrices and generated schemas), adapter libraries (SQLAlchemy,
  Libcloud, Knex), agent-facing docs (llms.txt, Context7), and contract testing for drift.

## Findings

### What exists today

repobuddy ships one `many` interface, `project-tracker.capabilities`, and three implementations keyed `github`,
`gitlab`, and `jira` (E1, E2). Each implementation is an adapter: under one heading per operation it gives the command
that does it on that tracker (E3). The skills own the workflow and call the operations by heading. The point of one
shared name is that a new tracker needs no change to the skills (E4). The Asana implementation the issue mentions is
planned in cyber-asana, not shipped (E1).

The reference system already supplies the machinery: interfaces with required and optional sections, `many` keys,
`check`, `implementations` with each one's unsupported sections, and a create flow that stubs each section
`**Unsupported.**` (E9). The spec's own example of implementing another skill's interface is the Asana tracker.

### Where the convention falls short

- Facts about the system itself are written differently in each implementation: required tool versions, the version a
  feature arrived in, tiers, whether a command was ever run against the system (E5). None has a doc link or a verified
  date.
- Facts that belong to the system leak into the skills: how to detect a tracker from the remote, the fallback list
  (E6). So adding Jira still left skills naming only GitHub and GitLab.
- A partial level exists only as an unofficial `Workaround:` line (E2), where adapter libraries name it "emulated"
  (E17).

### Two purposes under one name

The issue defines a capability reference as what an author reads to generate or customize a skill for a system. What
repobuddy ships is read at run time by a skill that does not change (E3, E4). OpenAPI and Arazzo draw the same line:
one document says what the system can do, another describes a workflow over it (E12). The runtime form is the one with
a consumer, a shape, and a check; the authoring form, a summary with links for someone writing a skill, is what llms.txt
already offers (E16) and needs no reference-system support beyond a plain reference.

### What recurs elsewhere

Across LSP, MCP, BCD, Terraform, and adapter libraries (E10 to E17): a stable id and a summary per capability; a
support level, with absent meaning unsupported; partial or emulated support with a required note; the version a
capability arrived in and was deprecated in; a link to the system's own docs; and a version for the description's
format kept apart from the system's version.

### Staying current

Ranked by strength: generated by the system (Terraform, MCP `tools/list`), negotiated at run time (LSP, MCP), tested by
a collector against the real system (BCD), contract-tested in CI (Dredd), then schema linting and review (E11 to E15,
E18). Hand-maintained data goes stale: BCD's manual mirroring did (E14). The first two cannot apply to prose that holds
commands for a CLI; the third and fourth can, as a probe the implementation carries. No spec found records a "last
verified" date, so one would be ours to define (E18).

### What "system" covers

Nothing in the mechanism depends on the system being remote. A local CLI (`gh`, `glab`) is already part of each
tracker's description (E5). A harness is different in this repository: harness facts are encoded in code with research
citations (`packages/cyber-agentkit/AGENTS.md`), so a harness capability reference would duplicate that source.

## Contradictions

- The issue's definition (input for generating a skill) and the shipped practice (an adapter read at run time) differ
  (E3). Resolved in the conclusion in favour of the shipped practice, with authoring as a use of it.

## Open questions

- Whether a probe section can be checked without a live system in CI.
- Whether the record shapes an interface defines (repobuddy's Item ref) belong in the reference system or stay in the
  interface's prose.
